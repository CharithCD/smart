# Plan: Next.js project with auth and working CRUD for the Infrastructure module

**Date**: 2026-09-28
**Goal**: A running Next.js app where a user can sign up and log in, create a company, run an infrastructure assessment (context → needs → ratings → results), and list, view, edit and delete their own assessments, all stored in Postgres.
**Follows**: [research/2026-09-28-nextjs-stack-and-conventions.md](../research/2026-09-28-nextjs-stack-and-conventions.md)

## Scope

**In:**
- **Auth:** email + password sign-up, login and logout with Better Auth.
  - Every page except login and signup requires a session.
  - Users only see and change their own companies.
  - Each user gets a `role` (`founder` by default; `researcher` is set by hand for now).
- **Company CRUD:** the parent record, whose shared profile holds stage, product type and operating mode.
- **Infrastructure assessment CRUD:**
  - create a draft
  - edit it in the wizard (saved on every step)
  - complete it (the server computes the score)
  - view the results
  - list past assessments
  - delete one
- Port the prototype's scoring logic into a typed, pure engine with tests.

**Out (later slices):**
- **Auth extras:** email verification, password reset (both need an email service), social login, and admin pages for researchers.
- Specific questions per criterion. This slice keeps the prototype's 0–5 rating per criterion.
- The N4 plan with LKR costs.
- Gemini report, RAG, uploads and embeddings.
- The other 3 modules, the dashboard, and deployment.

## Decisions for this slice

| Topic | Decision |
|---|---|
| Where | Commit the current prototype to git, move it to `prototype/` (read-only reference until it's ported), and scaffold Next.js at the repo root. |
| Local database | `npx prisma dev`, a local Prisma Postgres with no account needed. It "accepts one connection at a time", which is fine for one developer. The hosted Singapore database comes when we deploy. |
| Auth library | **Better Auth**, email + password, using the Prisma adapter. Sessions are stored in the database. |
| Auth checks | `proxy.ts` only checks for the session cookie and redirects to `/login`. The real check is `requireUser()` in `lib/dal.ts` (`auth.api.getSession`), and `requireCompany(id)` also checks ownership. Every DAL function calls one of these, as the Next.js auth guide recommends. |
| Login/signup forms | The same React Hook Form + Zod + shadcn `Field` pattern as every other form. They call Better Auth's browser client (`authClient.signIn.email` / `signUp.email`) and then `router.push('/companies')`. |
| Completed assessments | **Read-only.** To redo one, start a new assessment, so the evaluation data (κ/MAE) never changes after the fact. Drafts can be edited and deleted, and completed ones can be deleted. |
| Profile values | One set of IDs in `features/profile/options.ts`, taken from the engine's IDs (`prelaunch`, `saas`, `hybrid`, …). This fixes the prototype's "Pre-launch" vs `prelaunch` mismatch. |
| Operating mode | Moves to the company profile (shared), not the infra wizard. |

## Data model (this slice)

`User`, `Session`, `Account` and `Verification` are **generated by Better Auth's CLI** into `schema.prisma`. We then add `role` and the `companies` relation to `User`.

```prisma
// on the generated User model, add:
//   role      String    @default("founder")   // "founder" | "researcher"
//   companies Company[]

model Company {
  id            String       @id @default(cuid())
  ownerId       String
  owner         User         @relation(fields: [ownerId], references: [id], onDelete: Cascade)
  name          String
  industry      String?
  stage         String       // ids from features/profile/options.ts
  productType   String
  operatingMode String
  budgetLkr     Int?
  assessments   Assessment[]
  createdAt     DateTime     @default(now())
  updatedAt     DateTime     @updatedAt
  @@index([ownerId])
}

model Assessment {
  id            String   @id @default(cuid())
  companyId     String
  company       Company  @relation(fields: [companyId], references: [id], onDelete: Cascade)
  module        String   // "infrastructure"
  status        String   @default("draft") // "draft" | "completed"
  inputs        Json     // { context, ratings } validated by features/infrastructure/schema.ts
  result        Json?    // engine output, set on complete
  engineVersion String?
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt
  @@index([companyId, module])
}
```

```ts
// src/lib/dal.ts: the only place that decides "who is this and may they touch it"
import 'server-only';
import { cache } from 'react';
import { headers } from 'next/headers';
import { redirect, notFound } from 'next/navigation';
import { auth } from './auth';
import { db } from './db';

export const requireUser = cache(async () => {
  const session = await auth.api.getSession({ headers: await headers() });
  if (!session) redirect('/login');
  return session.user;
});

export async function requireCompany(companyId: string) {
  const user = await requireUser();
  const company = await db.company.findFirst({ where: { id: companyId, ownerId: user.id } });
  if (!company) notFound();
  return company;
}
```

**The DAL functions** are all in `features/infrastructure/data.ts`, and every one of them starts with `requireCompany(companyId)`:
- `listAssessments(companyId)`
- `getAssessment(companyId, id)`
- `createDraft(companyId)`
- `saveDraft(companyId, id, inputs)`
- `completeAssessment(companyId, id, inputs)`
- `deleteAssessment(companyId, id)`

**The actions** are plain and follow the forms rules in the conventions doc: `Schema.parse`, then call the DAL, then `revalidatePath`/`redirect`.
